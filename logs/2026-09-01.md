- **coreDAQ-LIN "buffer time" root cause found and quantified:
  `raw_data/2026-09-01-bandpassfilter1527nm.json`** (LinaWindow Response
  Sweep, start 1527 nm, stop 1570 nm, speed 5.0 nm/s -> sweep duration
  8.60 s; samples/ch 1,000,000 @ 100,000 Hz -> capture duration 10.00 s;
  same mismatch the GUI itself flags). Carolina's theory: the coreDAQ
  starts recording well before the laser sweep physically begins, so the
  GUI's "LINEAR model" wavelength axis (which naively maps sample index
  across the nominal start/stop range over the full capture duration) is
  wrong -- confirmed by pointing a narrow bandpass filter at the sweep's
  own *start* wavelength (1527 nm) and testing whether it lights up at
  the start or middle of the recording.
  - New tool `tools/find_coredaq_buffer_time.py`: Ch2+Ch4 (smoothed, sum
    cancels the interference fringe and tracks total transmitted power)
    stays pinned near its transmission maximum continuously from
    recording start (t=0) until a sharp fall at **t ~ 2.00-2.02 s**
    (90%/50% edge crossings), then flat zero for the remaining ~8 s --
    i.e. the laser sits still at 1527 nm (inside the filter's passband)
    for ~2 s before the sweep starts actually ramping, then leaves the
    passband within ~35 ms once it does move (10-90% edge width 0.0365 s
    x 5 nm/s ~= 183 pm, same order as the ~280 pm FWHM measured earlier
    today for the other filter -- consistent).
  - **Buffer time ~= 2.0 s.** Plot:
    `results/2026-09-01/bandpassfilter1527nm_buffertime.png`.
  - **Important: this is NOT the same as the GUI's own flagged mismatch**
    (capture 10.00 s - sweep 8.60 s = 1.4 s). The measured buffer time
    (~2.0 s) is ~0.6 s larger than that naive difference, meaning there's
    a real extra start-of-sweep latency (trigger/command propagation,
    laser ramp-up, etc.) on top of the capture/sweep duration mismatch --
    simply setting capture duration = sweep duration (the GUI's own
    suggested fix) would NOT be enough; it would still lose the first
    ~2 s of the sweep at the *start*. **Consequence for the "1560 nm
    filter shows no signal" observation**: with buffer_time ~2.0 s and
    the current 10.00 s capture, real recorded wavelength only reaches
    ~1527 + 5*(10.0-2.0) = 1567 nm before the recording ends -- i.e. the
    last ~3 nm of the intended 1527-1570 nm range is never actually
    recorded. Combined with the ~17 nm labeling offset found on the other
    filter above, a "1560 nm"-labeled filter with a similar true-center
    offset would sit beyond that ~1567 nm reach, which alone would
    explain the missing signal without needing a larger buffer time.
  - **Recommended fix**: delay the actual coreDAQ sample recording by
    ~2.0 s after the sweep-start trigger (not just match capture length
    to sweep length), so recording starts exactly when the sweep starts
    moving.

    (FWHM 351 pm) -- fix looked confirmed. The "1560 nm" filter showed no
    peak at all (Ch2+Ch4 envelope never rose above the negative noise

    just sits above 1570 nm, outside the swept window -- reasoning: "the
    wavelength axis spans exactly 1520.0000-1570.0000 nm, so the full

    axis is *always* `linspace(start, stop, n)` built after the buffer
    crop, regardless of whether the real optical sweep actually finished
    within the recorded samples -- it is not evidence of real coverage.

    sweep reaches the higher wavelengths, and the tail of that
    "1520-1570 nm" label is fake, assigned to samples that were never
    actually captured there.

  - **Correct answer to "kann ich die coreDAQ-Messzeit verlängern?":
    yes -- raise Samples/ch** (keep Rate and Start/Stop 1520-1570 nm
    unchanged). 1,200,000 samples/ch was enough to capture the full
    sweep this time (833,333 pts post-crop, both peaks land well inside

    `samples/rate - buffer_time_s >= (stop-start)/speed`; if Auto-sized

    worth double-checking against `lina_window.py:752-761`.

- **Root cause of the cutoff nailed down: coreDAQ-1 (LIN) arming is
  always manual, never Auto.** The "Samples/ch" + "Rate (Hz)" box for
  this capture device has no Auto-sized mode -- capture duration is
  rigidly `samples / rate`, so this was never covered by the
  auto-padding fix logged above (that padding only applies when
  Auto-sized arming is available/used). With the defaults (1,000,000
  samples @ 100,000 Hz = 10 s capture) and a 10 s sweep itself
  (1520->1570 nm @ 5 nm/s), cropping the new 2 s buffer time off the
  front leaves only 8 s of real sweep data -- covering just
  1520 + 5*8 = **1560 nm**, not 1570 nm. The "1560 nm"-labeled filter
  (real center likely higher, given the ~5-17 nm positive offsets found
  on every filter above) fell right outside that truncated window --
  same mechanism as the very buffer-time bug fixed earlier today, just
  showing up again downstream because the sample count wasn't
  re-derived after adding the buffer crop.

  **Formula (manual coreDAQ-1 arming, general form):**

  | Quantity | Value (this case) |
  |---|---|
  | Sweep duration = (stop-start)/speed | 50 nm / 5 nm/s = 10 s |
  | + buffer time | + 2 s |
  | = required capture duration | 12 s |
  | x Rate | x 100,000 Hz |
  | = required Samples/ch | **>= 1,200,000** (set 1,300,000 for margin) |

  Matches exactly what raising Samples/ch to 1,200,000 fixed above.

  **Fix implemented: "Auto-fit" button added next to Samples/ch + Rate**
  for the coreDAQ-1 (LIN) manual arming box in `lina_window.py` --
  computes and fills in Samples/ch from the formula above (current
  Sweep start/stop/speed + Buffer time, at the currently-set Rate) so
  this doesn't need to be worked out by hand each time. The mismatch
  warning row (comparing capture against sweep + buffer, added with the

  any manual edit.
